一、已验证的 NPC／人类货物直接入座链
===================================

EDSBaggageSlotType：

- CatapultTray = 34
- PassengerSeat = 35
- PlaceForBackpack = 36

调用链：

sub_141193F30(slot, baggage, true)
  -> sub_141193FA0
  -> sub_141191E30

sub_141191E30 在 ownerType 为 5 或 6、slotType == 35 时建立 296 字节 placement group：

sub_1411856E0(group)
sub_1411857D0(group, 24, slot, &unk_144368830)
group+288 设置 bit 0x20
sub_141185B30(group, baggage)

其中 unk_144368830 = 0x18，模式／容量为 24。

sub_141185B30：

- baggage+152 = slot
- baggage+160 = placement group
- 更新 baggage 状态
- 调用 sub_141231760

sub_141231760：

- 发出 MsgDsBaggageEvent，hash 0x697B90E5
- baggage+156 设为 true

该消息只处理碰撞类别 99，不负责实体挂接。

真正挂接发生于：

sub_1411C7CC0 / dirty queue sub_1411CE500
  -> sub_1411B2230

sub_1411B2230：

- 解析 baggage 子实体
- 解析 PassengerSeat 所属车辆父实体
- ownerType 5/6 使用 mode=1
- 调用 Entity_AttachToParentAndNotify(child, parent, mode)
- 发出内部事件和 MsgEntityTeleported

Entity_AttachToParentAndNotify = 0x140130900，核心为 0x1401303E0。它只执行实体父子关系／空间注册，没有 ActionGraph 上车动画。

已确认逻辑：

PassengerSeat 分配
  -> mode 24 placement group
  -> dirty/full refresh
  -> Entity_AttachToParentAndNotify
  -> MsgParentChanged + MsgEntityTeleported

这是一条“货物槽位分配后直接建立实体父子关系”的链，不是一段可复用的人类上车动画。

尚未静态闭合 AliveHuman 的上游 PassengerSeat 选择器。不要把 DSPlayerCatchBaggageWork 当作该选择器；它主要处理槽位 4–7、10–12、16、21、22，fallback 36，只检查了 35 的占用。

ProcessVehicleAttach 的三阶段状态在 rideOn+0x198：

stage 0：

- 解析车辆
- 启动 seat transition
- Entity_AttachToParentAndNotify(player, vehicle, 0)
- 分类上车方向
- 写 approach-specific seat state

- runtime+0x18B=1
- 原生左前方测试发生在 RideOn elapsed 3.24492 秒

RideOn Update：

- 0x140F99FEC 调用 ActionParams_QueryBoolEventByParamId(actionParams, 0xED)
- true 后进入原生完成尾声，最终 plugin+0x11A=2，进入 Drive

- 3.58276 s：RideOn next=2，Drive Enter

实体挂接、mount arrival、角色演算完成和 Drive 状态进入是不同层次。

三、0xED ActionGraph 事件链
========================

- rideOn+0x98 是 DSPlayerEntity。
- DSPlayerEntity vtable = 0x143233158。
- slot 20 = 0x140DBB9A0，映射 external ActionParam ID。
- DSPlayerEntity+0x8A8 指向 GraphAnimationManager。
- GraphAnimationManager vtable = 0x143128308。
- slot 28 = 0x140226EE0，查询 bool event。
- ActionParams_QueryBoolEventByParamId = 0x140DBEA20。

0xED 是动画时间区间跨过 SkeletonAnimationEventTag 后产生的 bool event，不是简单的 reached-end 字段。

强制 0xED 或直接把状态写成 Drive，只会推进玩家 RideOn 逻辑，不能保证停止已经启动的 CutIn Camera／presentation action。

五、最重要的新证据：上车镜头属于 DSCutInCamera 链
=================================================

RideOn ProcessVehicleAttach 在 0x140F9AFCC 调用：

sub_140E21880(
    qword_14623EA08,
    selectedActionHash,
    rideKind,
    8,
    vehicleTarget,
    false)

sub_140E21880：

- 在全局对象锁内写 pending action
- hash 位于 global+0xE8
- pending byte 位于 global+0x1E
- flags/mode 位于 global+0xF0
- target 引用位于 global+0xC8

消费者为 sub_140E229C0。

RTTI/vtable 证据：

- DSCutInCamera vtable = 0x143245018
- vtable slot 3（0x143245030）= sub_140E229C0

因此 sub_140E229C0 可以高可信识别为 DSCutInCamera_Update。

DSCutInCamera vtable：

- slot 0：0x140E228B0
- slot 1：0x1400A10E0
- slot 2：0x140E22920
- slot 3：0x140E229C0
- slot 4：0x140E248B0
- slot 5：0x140E24E00
- slot 6：0x140E277B0
- slot 7：0x1400A10E0
- slot 8：0x1400A10E0
- slot 9：0x140E25700
- slot 10：0x140E27570
- slot 11：0x14011E880

sub_140E229C0：

- 从 qword_14623EA08+30 取 pending request
- 读取 action hash、flags、variant ID
- 清除 pending 状态
- 在玩家 action resource 列表中按 hash 找资源
- 更新 CutInCamera 当前 action/resource/variant 字段
- 调用 sub_140E22F30 选择实际动作变体

sub_140E22F30 的反编译给出决定性证据：

- 构造 DSCameraBroadPhaseCollisionFilter
- 构造 cutincam::MyHitFilter
- 使用 pending target entity
- 执行摄像机 broad-phase collision 检查
- 在 action resource 的多个变体间选择
- 返回实际 cut-in action variant

当前已验证模型：

RideOn ProcessVehicleAttach
  -> 设置玩家 ActionGraph 参数
  -> 选择上车 action hash
  -> sub_140E21880 排队 CutIn action
  -> DSCutInCamera_Update
  -> 根据车辆 target 和相机碰撞选择 cut-in variant
  -> CutIn action 参与镜头演出和玩家动作
  -> 动画 event 0xED 到达后 RideOn 结束
  -> Drive Enter

这解释了为何玩家已经坐进车内仍保留镜头与等待：空间挂接和 RideOn 状态提前完成，并不会正常结束 DSCutInCamera 当前 action。

十、当前结论边界
================

已经可以肯定：

- NPC／人类货物瞬移入座是 PassengerSeat placement + entity attachment。
- 玩家上车不是同一套流程。
- 玩家在 ProcessVehicleAttach 很早就已经挂到车辆父实体。
- 冗长等待包含多个独立层：seat transition、mount arrival、fullgame 角色 descriptor、ActionGraph 0xED、DSCutInCamera cut-in action、RideOn→Drive。
- 仅传送玩家或仅写 Drive 状态无法正常结束 CutIn Camera。
- 合理介入点最终必须同时保证：玩家实体正常挂接并坐定、ActionGraph 进入合法 seated/Drive 结果、RideOn 正常退出、DSCutInCamera 正常结束并释放 target、驾驶镜头与输入正常恢复。
