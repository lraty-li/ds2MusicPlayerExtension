# 下一方向：参数包络干预方案

## 当前已确认边界

当前已确认的 C++ 层边界：
1. 状态机加速 (`plugin+0x11A=2`) 改变状态流转，但图不直接读取状态机字节
2. 动画状态 `5→1` 改写不对应图的直接控制位 `inner+0x2E0`
3. 相位 `inner+0x544` 改写不承担当前视觉过渡控制
4. `rideKind` 覆写发生在 OnEnter 参数写入之后
5. Presentation 压制不直接改变当前可见动画

**当前直接改变视觉启动链的路径：** 跳过 OnEnter。该路径同时会改动后续下车姿势链。

## 核心原因

Decima 动画图（可视化脚本系统）直接从**动作参数包络**（rideOn+0x98 → params block）读取值来驱动上车动画。
C++ 侧的任何状态机/动画状态/相位写入都无法影响这个图，因为图是独立的运行时系统。

## 新方案

### 核心思路

在 OnEnter 写入动作参数包络后，**立即恢复这些参数到上车前的值**。
这样动画图就收不到"上车动画启动"信号，不会加载上车剪辑。

### 实现步骤

1. Hook `OnEnter` (sub_140F98D00)
2. 调用前：保存参数包络中关键区域的值
3. 调用原始 OnEnter（获取参数设置和标志位）  
4. 调用后：恢复参数包络到保存的值
5. 继续现有 ProcessVehicleAttach gate forcing + FastDrive 路径

### 参数包络布局（实验观察）

已知的参数写入（相对于 params block 起始）：
```
| 偏移 | 值 | OnEnter 写入 |
|------|-----|-------------|
| +0x34C0 (flag) / +0x34D0 (value) | float = 0 | 不变（已为0）|
| +0x3730 (flag) / +0x3740 (value) | float = 0 | → -1.0 |
| +0x3760 (flag) / +0x3770 (value) | float = runtime+0x240 派生 | 变化 |
| +0x3790 (flag) / +0x37A0 (value) | float = 0 | 不变 |
| +0x3820 (flag) / +0x3830 (value) | float = 0 | 不变 |
| +0x3880 (flag) / +0x3890 (value) | float = 0 | 不变 |
| +0x3940 (flag) / +0x3950 (value) | float = rideKind scalar | 变化(关键!) |
| +0x3DC0 (flag) / +0x3DD0 (value) | float = 0 | → 1.0 |
| +0x53B0 (flag) / +0x53C0 (value) | float = 0 | 不变 |

标志区域（纯 flag 激活）：
+0x1030, +0x1060, +0x1090, +0x10C0, +0x10F0, +0x1120, +0x1150, +0x1180, +0x11B0, +0x11E0, +0x1210, +0x1510
```

### 风险

- 动作参数包络可能是共享的（被多个系统使用），恢复可能影响其他系统
- 参数的"默认值"可能取决于当前上下文（站立、行走等），简单恢复可能产生意外行为
- 某些 OnEnter 写入的参数可能是正常游戏所必需的

### 初始化方案

先实现**只读跟踪版本**：在 OnEnter hook 前后记录参数包络的关键值变化，
通过一次游戏运行验证哪些参数实际发生变化，然后只恢复这些参数。

关键跟踪参数（从 params block 起）：
- `[params + 0x34C0]` - 0x20 字节（flag + value 区域）
- `[params + 0x3730]` - 0x80 字节（多个 flag + value）
- `[params + 0x3940]` - 0x20 字节（rideKind flag + value）
- `[params + 0x3DC0]` - 0x20 字节
- `[params + 0x53B0]` - 0x20 字节
- `[params + 0x1030]` - 0x510 字节（12 个 flag，每个 0x68 间隔）
