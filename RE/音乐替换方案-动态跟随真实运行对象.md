# DS2 音乐替换方案：动态跟随真实运行对象

## 目标

目标仍然是音乐替换：

- 不关心播放器 UI 的具体实现
- 不伪造完整 `WwiseWemResource`
- 不改切歌逻辑
- 只在真实发声数据生成时，用外部音乐文件字节覆盖原始音乐字节

## 当前唯一可靠的前提

到目前为止，真正通过运行日志稳定成立的只有这条骨架：

- `sub_142693510`
- `sub_1426C4120`

这条链已经能稳定提供两类关键信息：

- 当前真实发声资源的 `wemId`
- 当前目标资源对应的 `segment`

因此，后续所有方案都必须以这两个运行时锚点为起点，而不能再从未命中的静态函数名出发。

## 旧路线为什么都不行

前面失败的共同原因，不是“音乐替换这个目标不对”，而是“固定 hook 点选错了”。

已经被运行日志否掉的实现方式包括：

- 直接把 `sub_142073210 / sub_1420741A0` 当成当前音乐主链
- 直接把这轮选中的 `sub_14206A490 / sub_14206FEF0` 当成当前音乐主链
- 先假设音乐一定走某个固定 submit 实现，再围绕它做替换

所以新的方案不能再建立在“静态上看起来像下一跳”的函数名上。

## 新方案

### 核心原则

不再预设固定函数地址，而是动态跟随真实运行对象。

也就是说：

1. 先用 `sub_1426C4120` 识别目标 `segment`
2. 再从真实对象的虚表里读取“当前实际会被调用的函数指针”
3. 对这个运行时真实落点做拦截
4. 最后再决定真正的字节覆写边界

### 第一层：路由确认层

这一层不做音乐覆写，只回答“当前音乐请求实际走到了哪里”。

应当动态读取两类真实对象：

- `off_14407FB20` 当前对象的 `vftable + 0x20`
- `qword_14619D918` 当前活动读设备的 `vftable + 0x20`

这里的重点不是函数名，而是：

- 当前这一刻真实被调用的函数指针是谁
- 它和目标 `segment` 是否属于同一条音乐请求

### 第二层：真实覆写层

当第一层确认真实运行边界后，再决定覆写点：

- 如果真实路径落到底层直读链
  - 就在真实命中的低层缓冲写回点按偏移覆写
- 如果真实路径落到 wrapper 且真的经过块写回
  - 就在 wrapper 的真实写回点按逻辑流偏移覆写

这里的原则始终不变：

- 游戏原本的对象、状态机、提交链保持不动
- 外部音乐文件只作为字节源
- 真正替换动作只发生在输出缓冲成型时

## 为什么这条路线才有机会成立

这条路线的优势不在于“更复杂”，而在于它不再赌静态推导的固定落点。

当前已经能确认：

- `sub_1426C4120` 的目标 `segment` 绑定是稳定的
- 下一跳存在虚表分发
- 固定函数地址版本已经多次被运行日志否掉

因此，只有“动态跟随真实运行对象”才符合当前已知事实。

## 明确排除

以下做法不再作为方案：

- 固定 hook 某一个静态 submit 函数，然后假设音乐一定经过它
- 为了替换音乐去伪造完整资源对象
- 先实现覆写，再反过来解释真实链路

## 下一轮验证目标

下一轮只需要验证三件事：

1. `sub_1426C4120` 命中目标 `segment` 后，真实被调用的 submit 函数指针是谁
2. 这个真实 submit 之后，第一个稳定的缓冲成型点在哪里
3. 这个点能否同时拿到：
   - 目标请求标识
   - 偏移
   - 输出缓冲

只要这三件事被跑通，音乐替换就能从“继续摸链路”进入“真正实现”。
