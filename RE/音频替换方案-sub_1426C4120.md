# 音频替换方案审阅稿：`sub_1426C4120 -> off_14407FB20[4]`

## 目标

目标只有一个：让游戏内播放器在播放当前曲目时，实际读取并输出目录中的外部音乐字节。

不关心：

- 播放器 UI 如何切歌
- 下一首按钮内部怎么实现
- 播放列表状态机如何推进

当前方案只讨论“当前曲目的音频字节替换边界”。

## 结论先行

当前唯一值得继续推进的主替换边界是：

- 上游命中与资源绑定：`sub_142693510 -> sub_1426C4120`
- 实际提交边界：`sub_1426C4120` 调用的运行时 `off_14407FB20` 槽位 `[4]`

这条路线是目前唯一同时满足以下两类条件的候选：

- 资源级关联键仍在现场
- 输出缓冲、写入长度、逻辑偏移三元组也在现场

因此，它是当前唯一能收敛成“理论上完整可实施”的主方案。

这里的“理论上完整可实施”指的是：

- 不需要再去猜更低层某个 submit 函数
- 不需要退化到只剩 package/chunk 的共享缓存层
- 不需要伪造完整 `WwiseWemResource`
- 只要补齐运行时槽位 `[4]` 的真实实现与完成契约，就能直接落成替换实现

## 证据分级

### 运行已命中

- `sub_142693510 -> sub_1426C4120` 已在当前目标操作流程里命中。
- `sub_1426C4120` 内部已经能稳定观察到：
  - `wemId`
  - `wemResource`
  - `streamHandle`
  - `segment`
- preview 与正式播放都能汇合到 `sub_1426C4120`。

### 静态候选

- `sub_1426C4120` 当前已静态补齐：
  - `streamObject + 0x30 -> WwiseWemResource*`
  - `streamObject + 0x38 -> segment 基偏移`
  - `segmentDesc + 0x00 -> 当前段相对偏移`
  - `segmentDesc + 0x0C -> 当前段长度`
  - `segmentDesc + 0x10 -> 当前段输出缓冲`
- `sub_1426C4120` 会把：
  - `resource + 0x10`
  - `resource + 0xC0`
  - `resource + 0xD0`
  装进提交给 `off_14407FB20[4]` 的参数与 transfer 结构。
- `InitStreamCacheSubmitterThread` 会把 `off_14407FB20` 从静态对象改成运行时对象 `a1 + 0x20`。

### 尚未升级到“已验证边界”

- 还没有记录到 `off_14407FB20` 运行时对象地址、vftable 地址、槽位 `[4]` 的真实函数指针。
- 还没有运行时证明 `segmentDesc + 0x10` 就是后续真实可听路径消费的缓冲。
- 还没有运行时证明在这个边界短路原始读请求后，完成句柄仍能按原链路被消费与释放。

## 为什么主方案选它

## 1. 它是第一个同时保留“资源键”和“输出三元组”的点

在 `sub_1426C4120` 现场，已经能同时拿到：

- 目标资源关联
  - `wemId`
  - `wemResource`
  - `streamHandle`
  - `segment`
- 输出三元组
  - 输出缓冲：`segmentDesc + 0x10`
  - 写入长度：`*(segmentDesc + 0x0C)`
  - 逻辑偏移：`*(segmentDesc + 0x00) + *(streamObject + 0x38)`

这正是“音频替换”所需的最小闭环。

## 2. 它比伪造完整 `WwiseWemResource` 更小

当前静态链表明：

- `sub_1426C4120` 已经拿到现成的 `WwiseWemResource*`
- 它只是把这个资源拆成读请求参数，再交给 `off_14407FB20[4]`

因此更小的边界不是：

- 预先构造完整 `WwiseWemResource`
- 再注册进全局表

而是：

- 保持原始 `WwiseWemResource*` 不动
- 只在“这个资源准备提交 segment 读请求”的时刻，改掉字节来源

这更符合“只做音乐替换，不接管播放器实现”。

## 3. 它比更低层读队列更稳

低层 `Win32ReadQueue_ExecuteRead` 这类点虽然机械上能看到：

- 文件偏移
- 输出缓冲
- 读取长度

但它已经丢掉了：

- `wemResource`
- `streamHandle`
- `request handle`
- `callbackCtx`

它最多只能回到 `fileView / segmentEntry`，还缺“目标曲目资源 -> 低层文件视图”的稳定桥。

所以它不是当前可直接实施的主边界。

## 4. 它比包装层最终写回更稳

`sub_1420741A0` 虽然静态上有：

- `dst`
- `len`
- `blockIndex + inBlockOffset`

但它面对的稳定键已经退化成：

- `packageId`
- `chunkIndex`

这更像共享包块缓存写回层，不再是曲目资源级边界。

如果在这里替换，误伤同包块其他消费者的风险明显更高。

## 方案正文

## 主边界

主边界定义为：

- 运行已命中上游：`sub_142693510 -> sub_1426C4120`
- 实际替换落点：`sub_1426C4120` 或它调用的运行时 `off_14407FB20[4]`

当前更推荐的实际落点是：

- 先记录 `off_14407FB20` 运行时对象和槽位 `[4]`
- 再 hook 该运行时真实函数

原因是：

- 运行时对象会替换掉静态 submitter
- 直接 hook 静态命名函数风险高

## 外部音乐替换逻辑

对命中的目标曲目，替换逻辑应当是：

1. 用 `wemId` 或 `wemResource` 判断“当前 segment 是否属于目标曲目”。
2. 计算当前请求的逻辑偏移：
   `logicalOffset = *(segmentDesc + 0x00) + *(streamObject + 0x38)`
3. 取当前段输出缓冲：
   `dst = *(segmentDesc + 0x10)`
4. 取当前段长度：
   `len = *(segmentDesc + 0x0C)`
5. 从外部音频文件的 `logicalOffset` 位置读取 `len` 字节写入 `dst`。
6. 若外部文件不足 `len`，尾部补零。
7. 让当前段在原有完成链上表现为“本次读请求已完成”。

这里最关键的是第 7 步。

前 1 到 6 步已经静态闭环。
第 7 步还差运行时确认，所以当前仍属于“主方案已选定，但未过实现闸门”。

## 为什么这个替换逻辑理论上成立

因为它不依赖顺序游标，不依赖“下一首”逻辑，也不依赖全局状态机。

它只依赖每一段请求自身携带的：

- 这是谁的资源
- 要写到哪里
- 写多少
- 这段对应外部文件的哪个逻辑偏移

所以它天然支持：

- preview
- 正式播放
- 下一首后的新曲目
- 同一曲目的多段分块推进

而不需要额外推断播放器状态。

## 实现形态

实现时只保留一条主假设，不并行保留多个未证实边界。

建议实现拆成两层：

### 第一层：观测与绑定

保留：

- `sub_142693510`
- `sub_1426C4120`

作用：

- 记录目标曲目的 `wemId / wemResource / streamHandle / segment`
- 记录 `off_14407FB20` 运行时对象、vftable、槽位 `[4]` 真函数指针
- 记录该槽位返回的句柄如何被后续链路消费

### 第二层：真正替换

只在运行时槽位 `[4]` 上做替换。

命中目标曲目时：

- 走外部文件读取
- 不命中时完全走原始链路

这样能保证：

- 非目标曲目零影响
- 旧播放器逻辑不需要重写

## 当前不能直接采用的方案

## 1. 伪造完整 `WwiseWemResource`

问题：

- 实现面太宽
- 会把目标扩大到资源构造和注册体系
- 不符合“只做音乐替换”

当前结论：

- 不是主方案
- 只保留为更重的备选路线

## 2. `sub_1420741A0` 包装层最终写回

问题：

- 资源键退化成 `(packageId, chunkIndex)`
- 更像共享缓存写回层
- 没有资源级唯一性保证

当前结论：

- 只能算静态观察点
- 不是主替换边界

## 3. `Win32ReadQueue_ExecuteRead`

问题：

- 虽有偏移/缓冲/长度
- 但缺 `wemResource / streamHandle -> fileView / segmentEntry` 的稳定映射

当前结论：

- 机械条件充分
- 资源关联不足
- 不是当前主边界

## 实现闸门

在开始写新 hook 前，必须同时满足：

- 当前目标操作流程里真实命中过
- 能稳定关联到当前目标资源，关联键至少满足其一：
  - `wemId`
  - `wemResource`
  - `segment`
  - `streamHandle`
  - 运行时虚表槽位真实函数指针
- 能拿到替换所需最小三元组：
  - 输出缓冲
  - 写入长度
  - 逻辑偏移或文件偏移

当前状态是：

- `sub_1426C4120` 已满足前两条中的大部分，并静态补齐三元组
- 但 `off_14407FB20[4]` 的运行时真实实现和完成契约还没记录

所以当前结论应写成：

- 主方案已确定
- 但还没过“可直接写实现”的最后闸门
