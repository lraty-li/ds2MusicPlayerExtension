**下面全是“静态候选”，还没有任何“运行已命中”。**

把这条链先当成一个更容易理解的模型：

`entryObjAt16 +64` 不是“声音已经在播了”，它更像“这首曲子对应的主资源指针”。  
`state+6424` 不是“UI 当前选中项”，也不是“字节流缓冲”，它更像“当前主链正在持有的运行时实例对象槽”。

可以把流程理解成：

```text
曲目条目
  -> 取出主资源(entryObjAt16 +64)
  -> 去“实例管理器”领一个运行时对象
  -> 把这个对象放进 state+6424
  -> 后续所有播放状态切换，都围着这个对象做虚表调用
  -> 不用了，再把这个对象还回管理器
```

更具体一点：

1. `MusicRuntime_ApplySelectedEntry(0x140C136D0)` 这类函数会从 `entryObjAt16 +64` 取资源，然后调用 `AcquireRuntimeObjectAndEnableOnStart(0x140AC5FB0)`。
2. 这个 `Acquire...` 不像“直接 new 一个对象”那么简单，它会先进 `sub_142689710`，由一个全局管理器 `qword_14A19EF50` 参与，拿到一个运行时对象，再给它写 `_on_start_ = 1`。
3. 返回的这个对象被写进 `state+6424`。所以 `state+6424` 的意义可以简单理解成：当前主播放链手上拿着的那个运行时对象。
4. 之后主循环 `sub_140C12330` 在合适状态下会对这个对象调用虚表 `+144`。这说明 `+144` 是“开始真正往下推进”的下一跳候选。
5. 当切歌、停用、清理时，会对同一个对象调用虚表 `+272`，必要时还会走 `+280`，最后 `ReleaseRuntimeObject(0x140AC60C0)` 把它交还给管理器。

所以这轮最核心的结论，其实只有一句话：

**`state+6424` 这条链已经静态证明是一条“资源 -> 运行时对象 -> 使用 -> 释放”的主链。**

你可以把三个虚表槽位先这样理解，但都只是工作理解，不是正式命名：

- `+144`：主循环里真正“继续往下做事”的槽位
- `+272`：切换/清理时反复用到的槽位
- `+280`：在位置/切换相关分支里用到的另一条控制槽位

现在还**不能**下结论的地方是：

- `state+6424` 一定是不是“新建对象”
- 它一定是不是“复用对象”
- 它一定就是哪一个精确类型
- `+144 / +272 / +280` 的精确语义是不是 Play/Stop/Seek
- `_on_start_` 最终到底是哪一层真正消费
- 这里是不是已经到了可做字节替换的边界

目前最像的静态类型候选是：这个对象落在 `SoundInstance` 体系里，而且很可能是 `WwiseSimpleSoundInstance` 分支；但这还差最后一跳闭环，所以现在只能当“强静态候选”，不能当结论。
